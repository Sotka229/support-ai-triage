# Прогон PoC на настоящей LLM

Мок-генератор удобен для тестов, но он не проверяет главное утверждение архитектуры: что
валидаторы и политика удержат систему, когда текст порождает модель, а не наш собственный код.
Шаблон цитирует источник дословно, поэтому его groundedness тривиально высокий, и prompt
injection ему нечем навредить. Поэтому PoC умеет работать с реальной локальной моделью.

```bash
python demo.py --llm ollama:llama3.1:8b
```

Контур self-hosted: модель крутится локально через [Ollama](https://ollama.com), наружу не уходит
ничего. Адаптер — [`src/triage/llm_ollama.py`](../src/triage/llm_ollama.py), стандартная библиотека,
без зависимостей. Класс объявляет `is_external = False`, поэтому запрет `block_external_llm`
(тикеты с платёжными данными) его не касается — это машиночитаемое свойство, а не комментарий.

## Что показал прогон

Железо: CPU-инференс, без GPU-ускорения (Radeon 780M, ROCm не задействован), 31 ГБ RAM.

| Модель | Время генерации | Итог |
|---|---:|---|
| `llama3.1:8b` | ~28 с на черновик | ответ по делу, автозакрытие сработало |
| `qwen3.5:9b-q4_K_M`, reasoning включён | 67 с | **пустой ответ**, `done_reason=length` |
| `qwen3.5:9b-q4_K_M`, `think: false` | 11 с | ответ по делу |

Поведение всех четырёх сценариев демо на живой модели совпало с прогоном на моке: 3 решения из 9
без оператора, критичный тикет ушёл в `FRAUD_TEAM` без вызова LLM, аудит-лог цел, PII не утекли.

## Находка 1: reasoning-модель съедает бюджет и возвращает пустоту

`qwen3.5` потратила все 400 токенов `num_predict` на внутреннее рассуждение: Ollama вернула
`eval_count=400`, `done_reason="length"` и **пустое** поле `response` — рассуждение уехало в
отдельное поле. Для генерации черновика по готовому фрагменту базы знаний рассуждение не нужно,
поэтому адаптер по умолчанию шлёт `think: false`; это ещё и вдвое быстрее.

Важно, что PoC при этом повёл себя правильно и без специальной обработки: пустой ответ — это
`LLMUnavailable`, то есть отказ, а не пустой черновик. Тикет ушёл оператору. Если бы код считал
пустую строку валидным черновиком, политика получила бы формально корректный объект без единого
утверждения и могла бы его отправить. Тесты на это: `test_empty_model_answer_is_a_failure_not_an_empty_draft`,
`test_answer_that_is_only_reasoning_is_a_failure`.

## Находка 2: валидатор groundedness слабее, чем кажется, и слабеет с ростом k

Замер на одном и том же наборе фрагментов (`kb.search(text, k=3)`, как в пайплайне):

| Черновик | groundedness | Вердикт |
|---|---:|---|
| Мок (дословный пересказ источника) | 1.000 | принят, ожидаемо |
| Живая `llama3.1:8b` (свободный пересказ) | 1.000 | принят — валидатор не наказывает за перефразирование, это правильно |
| Контроль: ответ из другой темы («заказ в пути») | 0.333 | отклонён, правильно |
| Контроль: обещание денег | 0.000 + правило `refund_promise` | отклонён дважды, правильно |
| **Контроль: правдоподобная выдумка** («пароль восстановится сам в течение 24 часов») | **1.000** | **принят — ошибка** |

Последняя строка — реальный дефект. Утверждение прямо противоречит базе знаний (там сказано
запросить письмо повторно, а не ждать сутки), но состоит из лексики источника, а `groundedness`
считает долю предложений, чьи словоформы пересекаются с объединённым текстом фрагментов. Логическое
следование не проверяется вообще.

Отдельное наблюдение, которое видно только на прогоне: **та же выдумка на одном фрагменте
получает 0.0, а на трёх — 1.000**. Источником для сравнения служит объединение фрагментов, поэтому
чем больше `k` у ретривера, тем шире словарь и тем легче любому связному тексту набрать
пересечение. Параметр качества поиска напрямую ослабляет валидатор безопасности — при переходе на
гибридный ретривер с `k=20` и reranker эта проверка выродится окончательно.

Разрыв зафиксирован исполняемым кодом, а не абзацем: [`tests/test_safety_limits.py`](../tests/test_safety_limits.py),
класс `TestKnownGap`. Целевой тест помечен `xfail(strict=True)` — когда groundedness заменят на
NLI-проверку утверждений против каждого фрагмента отдельно, тест начнёт проходить, прогон
упадёт и заставит снять пометку осознанно.

Практический вывод для раскатки: до появления NLI-проверки автозакрытие нельзя включать шире
allowlist-категорий с короткими шаблонными ответами, а `k` для генерации нужно держать
минимальным (1–3 фрагмента), даже если ретривер способен вернуть больше.

## Что это не доказывает

Прогон на 4 сценариях и двух моделях не является оценкой качества: нет ни выборки, ни разметки,
ни статистики. Он доказывает ровно одно — контракт компонентов держится на настоящей модели так
же, как на моке, а слабое место в валидаторе измерено, а не предположено. Полноценная валидация
описана в [ml.md](ml.md).
